# Bluence incremental application contract

## Release 1: supplied E1 welcome
The original layout, centered logo, typography, photographs and CSS are retained. All public assets are local. E2 and E4 have same-origin entry routes with honest unavailable states; they do not create accounts, drafts, results or actions. E7 content is displayed in the supplied accessible dialogs. The previous external-host adapter and Business link were removed. No legacy application user data was supplied or imported.

## Source authority
Journey V2 controls behavior; Sitemap V3 controls placement. The included Section E revision dated 26 October adds explicit later corrections: input-coverage detail bands (not accuracy), integrated task-specific Copilot and day-30 priority gap-filling. The owner's current instruction preserves this centered welcome design. Keep existing stable route/record identifiers as more sections are added.

## Existing data
Never clear or overwrite browser or server records on navigation, application startup or deployment. `bluence.navigation.v1` holds navigation only and preserves unknown keys. It is not authentication or action consent and must not be promoted into either. Existing external app records remain untouched. No implemented assessment or cross-device resume is claimed for this release.

## Future record relationships
Account -> assessment draft -> versioned calculation snapshot. Starting point references the first saved snapshot; first durable save anchors the day-30 check-up. Pending action intent references the actual result and selected catalog action and survives authentication cancellation. Authentication restores identity, never creates fresh consent. An action instance owns check-ins; check-ups reference confirmed input revisions and resulting snapshots. Goals are optional only after the first completed check-up. Today reads these same owning records; no duplicate page-specific stores.

## Future server requirements
Use authorized server drafts and records, idempotent commands, revision checks, atomic first-save/action acceptance where possible and honest partial success otherwise. Draft resume must restore original inputs and origin. Never derive identity from cookies or navigation state. The archived integration files are historical reference only: do not enable development identity fallback or old ChatGPT authentication as Bluence authentication. Do not reset first-save date on refinement or action changes. Never subtract reported actions from the footprint. Confirm material comparison-boundary changes and preserve original history.

## Gradual extension
Replace the unavailable estimate/sign-in surfaces at their existing `/personal/estimate` and `/personal/sign-in` routes as those sections are implemented. Preserve the E1 visual identity. Today is now implemented; replace the clearly disclosed Footprint, Actions and check-up destination boundaries as their sections arrive. Do not expose empty signed-in tabs or recreate retired F3/F5/F6/U2/U5 workflows. Existing full source and reference documents remain in Git for future work.

## Release 2: T1 Today
The authoritative T specification is retained in `docs/references/18-Bluence_UI_Structure_Section_T.md`. T1 implements the ordered next task, status line, up to three active actions, shared check-in editor, factual feedback, a single suggestion, remembered declines, optional reminder preferences, hotspot, completed-review summary, estimate-improvement link and supporting links. The existing E1 visuals and assets are retained; its navigation gains Preview Today.

`lib/personal/domain.ts` owns the Journey, Action, CheckIn, Result, Review, suggestion and draft relationships. Today reads these records and issues commands; it does not maintain a separate activity ledger. `components/personal/check-in.tsx` is the reusable P3 editor for future Actions integration. IDs, original first-save dates, existing records and correction history remain intact. A report updates activity only, never subtracts carbon from the saved estimate. Repeated reports and corrections are distinct. Optional F2 gaps never outrank the active loop, and optional review adaptation never makes a completed review incomplete.

`lib/personal/store.ts` is a replaceable browser-local adapter. `bluence.personal.v1` is reserved for real journey state; `bluence.example.<scenario>.v1` keys are explicitly illustrative and separate. No samples are automatically written into the personal key. Reads never clear storage. Commands use revisions and event IDs; Web Locks serialize supported browsers across tabs. Without Web Locks, revision checks remain, but fully atomic cross-tab writes are not guaranteed. A server adapter must supply transactional ownership and idempotency before multi-device use. Storage denial, corruption and quota failures do not replace existing data or claim success. Drafts are saved as edits occur; Cancel explicitly discards the current check-in draft. Undo is revision-guarded and may not overwrite intervening changes.

Routes preserve sample context and same-origin navigation. E/F/P/G destinations that are not built open explicit unavailable boundaries; they do not fabricate calculations, account state or review completion. The Today action controls are functional within the browser-local model. The example selector provides weekly, first-action, day-30, interrupted, quiet, paused, completed and returning states for review.

No real authentication, calculation, email dispatch or model endpoint is integrated. Copilot controls provide ordinary manual fallback and disclose unavailability. Reminder preferences keep delivery off. Sample numerical results are labelled illustrative, not presented as personal or recalculated data. The detailed F/P/G pages, account services and authenticated durable storage remain future sections.

## Release 4: Actions (Section P)
The complete Section P reference is retained in `docs/references/16-Bluence_UI_Structure_Section_P.md`. P1 overview and P3 action detail now replace the previous destination boundaries. P2 optional goals and P5 proposal review are available only after a completed check-up; P4 alternatives are contextual to the current action set. Routes preserve sample context and origin. Today's layout/photo and Welcome are unchanged. Shared check-in controls now support an optional note.

Actions, reports, goal and weekly schedule belong to the existing Journey record. Maximum three active commitments applies to adding, swapping, reopening and resuming. Replacement pauses the selected old action and retains its history. Removal is soft; state changes and report corrections keep original records and offer revision-guarded Undo. New reports and corrections remain distinct. Historical report dates and reporting-period boundaries are immutable. Weekly changes preserve reported periods, use a contiguous transition where needed, and never reset the first-save/check-up anchor. Occurrence scheduling is separate from the weekly reporting rhythm.

Goals use an explicit proposed/current review and stale-revision protection. Saving a goal does not change actions, confirmed estimates, assessment drafts or completed reviews. No invented numerical forecast or savings is shown. Sample catalog suggestions retain declines and duplicate protection. Personal empty state does not fabricate recommendations. Copilot and email delivery remain unavailable; manual action management works. Authentication, carbon calculations, server storage and cross-device sync remain future integrations.

Actions tests cover capacity, resume/swap, duplicate acceptance, historical corrections, contiguous schedule transitions, date validation, goal eligibility/revisions and isolation of estimates/reviews. Browser QA covered adding reports, correction/Undo and reload persistence, goal review/save, fourth-action capacity replacement, and both visual themes.
